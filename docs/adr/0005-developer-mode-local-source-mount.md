# 0005-本机源码目录直接挂载，不复制进扩展根（原「开发者模式」）

> **状态：已实施**（决策于「扩展市场开放给第三方开发者」设计讨论，2026-09；术语见 `CONTEXT.md`「扩展与市场」）。

扩展的调试回路今天只有两条，都不够用：**本地安装**（把 `.xhpack` 解包复制进扩展根，改源码不生效，每次要重打包重装）和**离线预览**（浏览器里跑 mock 桥，拿不到真实数据、真实权限与 service 后端、也不在宿主内）。要开放第三方生态，「写完立刻看到」这条回路必须在**真实宿主内**闭合，否则作者只能靠猜。

因此决策：**在真实宿主内直接加载本机源码目录，不复制进扩展根**。目录即真源，使用真实数据、真实权限与真实 service 后端，文件变更后自动重载。以该方式加载的扩展是**开发扩展**，不进「已装扩展」清单，也不参与市场更新与卸载流程。

**技术路径（已查证）**：宿主在运行期调用 `asset_protocol_scope().allow_directory(dir, true)` 即可——`Scope` 内部是 `Arc<ScopeInner>` + `Mutex<HashSet<Pattern>>`，协议 handler 注册时持有的是**同一个 Arc**，且每个请求实时校验、无路径缓存，因此新目录对已存在与新建的 iframe 都立即生效。开发目录写入 `AppConfig`，在启动 setup 中与数据根一并重放（scope 不落盘，重启必须重新注册）。变更检测沿用 `extensions_stamp` 已有的「FNV + mtime」轮询口径（现只扫 manifest，开发模式扫全目录），重载手段是**重设 iframe src 并附加 `?t=<mtime>` 破缓存**。

**被否方案**：①**复制安装 + 手动重载**——改源码不生效，不构成调试回路；②**junction 软链进扩展根以复用现有链路**——扫描侧虽把 junction 当普通目录，但 asset 侧会先 canonicalize 归到真实路径，不在 scope 内一律 403（实测）；③**内部 loopback HTTP 服务**——origin 由 `asset.localhost` 变为 `127.0.0.1:<port>`，扩展自身的 localStorage/IndexedDB 与生产环境隔离，且需自写路径穿越防护与端口鉴权，收益不抵成本。

**代价（接受）**：asset 作用域是**全局单例**，放开某个开发目录意味着该目录对**所有**扩展 iframe 可见——这条安全边界是否收紧（白名单 scope vs 扩展内容改用独立 origin）属独立决策，不在本 ADR 范围；注册时目录必须已存在（否则拿不到规范化模式变体）；含 `..` 的资源 URL 一律 403；重载会丢失扩展内的临时状态。

**落点**：**目录管理（增删）在扩展中心「我的扩展」标签页**（与「已安装 / 市场」并列，v0.6.x 从设置迁出——目录清单与「装了什么扩展」是同一件事，放在扩展中心才找得到；开发目录只在那一页露出，不进「已安装」）。**没有开关，登记即加载**：添加目录后立即放行作用域并加载，移除即撤销；该标签页对所有用户始终可见。发布入口在源码已加载时出现，能否真正发布由发布流程里的**开发者认证**把关（与本地调试无关）。

## 修订：取消「开发者模式」开关（v0.6.x）

初版把直挂做成 **opt-in 开关**（`dev_mode_enabled`，默认关闭，关着时已登记目录不加载、也没有发布入口）。实测下来这个开关是**净负担**：「我的扩展」这个入口存在的意义就是让作者**先在本机调试**，加进来却要先去找开关、关着还看到一行「当前不会被加载」，既费解又制造「移除算不算生效」这类无意义状态；而且它让「添加」与「加载」两个动作在用户心智里分家，却没有任何实际收益——用户点开目录选择器本身就是显式同意。

因此：**开关删除**（命令 `set_dev_mode_enabled` 一并移除，`DevModeStatus.enabled` 恒为 `true` 仅作旧前端兼容字段保留；`AppConfig.dev_mode_enabled` 标为废弃、读到即忽略）。安全边界不变——作用域只放行**用户显式添加**的目录，其余仍按上文「代价（接受）」那条处理。若将来确需「临时关掉全部本机源码目录」，再以新决策加回（不要复活这个开关）。

## 修订：落盘与交付的目录路径必须归一（v0.6.2）

`add_dev_extension` 原先把 `canonicalize()` 的结果**直接写进** `dev_extensions`，而 Windows 的 `canonicalize` 返回 verbatim（命名空间）形式 `\\?\A:\…`。这个前缀对宿主自己的 `fs` 调用无害，**一交给外部程序就出事**：service 扩展的后端由宿主起 Node 执行（`service.rs::start_service`），Node 的 CJS 加载器读不了带前缀的**脚本路径**——它把 `\\?\A:\…\backend\server.js` 拆错，跑去 `lstat` 盘符 `A:` 得 `EISDIR` 后 `exit 1`，后端在模块初始化阶段就死（已装扩展走 `extensions_root().join(id)`，天然无前缀，所以只有直挂的开发目录中招）。而当时后端 stdout/stderr 是 `Stdio::null()`，宿主侧只剩一个 `serviceReady=false`，界面上表现为「像在下载 Node」——**静默才是这次真正的放大器**。

因此定口径：**凡是要落盘、要展示、要交给外部进程的路径，一律经 `paths::simplify_path`（剥 `\\?\` / `\\?\UNC\`；含 `.`/`..` 组件与 `Volume{…}` 设备路径不剥）或 `paths::simplify_existing`（简化后仍可访问才采用，兜超长路径）**。落点五处：登记时落盘归一、`apply_dev_extensions` / `dev_mode_status` / `dev_extensions_stamp` 读取时归一（历史配置自愈，用户不必再手改 `app.json`）、`ext_protocol::resolve_ext_dir` 出口统一归一（一处覆盖 service / 打开目录 / storage / 打包 / 预检）、`load_extension` 的 `entry.dir` 与 `dev_mode_status().path` 口径一致（前端靠这两个字符串匹配「哪条直挂目录对应哪个已加载扩展」＝发布按钮的出现条件）、`service::backend_paths` 再兜一道（`argv[1]` 带前缀必死，`current_dir` 带前缀无害但统一口径）。同时给 service 后端补上 stdout/stderr 落盘（`<数据根>/logs/service/<扩展 id>.log`，单份 1MB 上限）与探活失败时的**退出码 + 日志尾部 20 行**。

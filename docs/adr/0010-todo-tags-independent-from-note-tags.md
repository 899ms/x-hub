# 0010-待办标签独立于笔记标签

> **状态：已实施（v0.6.5）**（决策于「待办功能升级」设计讨论，2026-09-21；实现见 `repo/todo_tag.rs` 与 `todos` 的标签桥能力。术语见 `CONTEXT.md` 的「待办」一节。）

## 问题

待办要支持「分类标签」。而笔记早已有一套标签：定义表 `tags`（`name UNIQUE`）与关联表 `note_tags`。待办标签是**复用这两张表**，还是**另起一套**？

## 决策

**另起一套。** 待办标签有自己的定义表与关联表，与笔记标签之间**没有任何同步关系**——改笔记的标签不会动待办的标签，反之亦然。

## 依据

- **用户明确否掉了共用**：「标签还是不能和笔记那边使用同一份，这样会让人感觉有点怪，等下笔记那边改了，突然发现待办的也该了，就感觉很莫名其妙」。
- 这个直觉是对的：共用一个定义表意味着**一次重命名/删除会横跨两个功能域生效**，用户在一个视图里做的动作在另一个视图里产生他看不到的后果。标签是「用户自己建立的分类词汇」，它的稳定性预期高于「表空间节省」。
- 两套标签的**交集很可能是空的**：笔记标签多为主题（读书、会议、灵感），待办标签多为归属与状态（客户A、紧急、生活）。强行合并只会让两边的选择列表都变长。

## 后果

- 定义表 `todo_tags` 需要自带 `color`（笔记的 `tags` 没有颜色列，本次不回头改它，避免牵动笔记功能）。
- 表命名与笔记那对不对称：笔记是 `tags`(定义) + `note_tags`(关联)，待办是 `todo_tags`(定义) + `todo_tag_links`(关联)。**这是刻意的**——`note_tags` 那对本身的命名就不对称，照抄只会让「`todo_tags` 到底是定义还是关联」永远需要查文档。改名时请保留这层区分。
- 将来若要做「按标签看全部内容（笔记 + 待办）」，需要跨两套标签做**名字匹配**而非 id 匹配。这是放弃共用换来的代价，已知并接受。
- 「清单（list）」是另一回事（单归属的互斥容器），本次不做，见 `CONTEXT.md` 的 `_Avoid_` 说明。

# 0009-周期待办：就地滚动 + 未来实例虚拟展开

> **状态：已决策，待实施**（决策于「待办功能升级」设计讨论，2026-09-21。术语见 `CONTEXT.md` 的「待办」一节。）

## 问题

待办要支持周期重复（每天喝水、每周一开周会、每月 1 日交房租）。这带来两个必须一起定的问题：

1. **完成一条周期待办之后，数据怎么变？**
2. **日历上要看到「未来还会发生」，这些未来条目从哪来？**

## 决策

**一、完成 = 就地滚动，不逐次留历史条目。**

勾选一条周期待办时：把 `due_at` 推进到**下一个未来时刻**（若下一个周期也已过去，继续跳，直到落在未来——即不补做逾期历史），`remind_at` 同步平移、`remind_fired` 复位，`repeat_done_count + 1`、`repeat_last_done_at = now`；**不置 `done`、不写 `completed_at`**，因此它永远不会进入「已完成」列表。

**二、未来实例是虚拟的，不落库。**

日历上的未来条目由前端按规则**即时算出**（纯函数展开，只算可视区间），库里始终只有「当前实例」这一行。

## 考虑过的方案

| 方案 | 为什么不选 |
|---|---|
| 每次完成插一条历史记录 | 「每天喝水」一个月就留下 30 条，待办列表会被历史淹没；而真正要的统计只是「共做了多少次 / 上次什么时候」，两个字段就够 |
| 完成即从列表消失，未来只在日历出现 | 用户失去「这条我还没做」的可见性，逾期无处显示 |
| 逐周期补做（逾期 3 天要点 3 次） | 惩罚用户，且「每天」在断档后失去意义 |
| 提前物化未来 N 个实例进 `todos` 表 | 表会膨胀；改规则或删除要批量清理；扩展桥 `todos.list` 会被灌满虚拟条目，第三方扩展无法区分真假 |

## 依据

- **有先例且语义完全一致**：`countdowns` 表的 `repeat_mode`（`once`/`daily`/`interval`）就是「就地推进 `end_at`」，`daily`/`interval` 永不置 `finished`。沿用同一模型与同一字段名，读者不需要学第二套心智。
- **「完成」与「做完一次」是两件事**：普通待办的 `done` 表示「这件事结束了」；周期待办的这次勾选表示「这一轮做完了，还会有下一轮」。共用一个布尔字段会让「已完成」列表被周期性内容污染，所以周期待办走独立完成路径。

## 后果

- `toggle` 语义分叉：周期待办需要独立的完成路径（如 `complete_recurring`），撤销勾选要把 `due_at` 回滚到本轮并 `repeat_done_count - 1`。
- **虚拟实例不可直接操作**：日历上拖拽改期对周期待办禁用（v1），改期只能进编辑弹层改规则。若将来要做「只改这一次」，需要引入「例外（exception）」概念并把它物化——这会显著抬高模型复杂度，故推迟到 v2。
- 结束条件（到某日 / 共 N 次）用尽后，**转为普通待办并停在最后一条**，不静默消失。
- 统计口径只有「累计次数 + 上次完成时间」，没有完成时间线；若将来需要审计，得另加历史表。
